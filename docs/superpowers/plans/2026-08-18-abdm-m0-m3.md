# ABDM M0-M3 implementation plan

Owner directive 2026-08-18: "go ahead with india host name. and complete everything M0123."

Spec + defect analysis: `docs/connect/abdm/V3-SPEC-RECONCILIATION.md`. Module note: `vault/modules/ABDM.md`.
Everything lands behind the existing flags (`CONNECT_FLAG`, `CONNECT_HIP_FLAG`) plus a new
`ABDM_M1_FLAG` for the ABHA surface, all default OFF.

## Decisions taken

- **India hostname assumed.** All ABDM callbacks are addressed at a single configurable base,
  `ABDM_CALLBACK_BASE` (e.g. `https://abdm.stewardmd.in`). The receiver is implemented as Pages
  Functions routes under `/api/v3/...` - the shape ABDM appends, and `/api/*` already bypasses the
  coming-soon gate - so the same code serves either a Cloudflare
  India-region custom domain or an India-hosted forwarder that proxies to it. No handler changes
  either way. NHA confirmation is not being waited on.
- **Reuse over rewrite.** `state.js` (txn/consent/buffer state machine), `consent.js` (artefact
  verify), `hip.js` (discovery/serve/consent store), `hiu.js` (consent init/HI request/consume),
  `fidelius.js` (crypto), `no-phi.js` (residency guard) and `audit.js` all stay. What gets rebuilt is
  the **transport**: the single JWS ingress becomes the real V3 callback paths.
- **Unstructured FHIR first.** Bundles carry a DocumentReference/Binary attachment; the builder is
  pluggable so structured coded resources can replace attachments per HI type later. ABDM allows this
  ("integrators can start with simple bundles with attachments").
- **ABHA is never stored raw.** Only `patient_abha_hash` (existing HMAC pseudonym) and last-4 of the
  number. The ABHA address is needed later by HIP linking, so it is stored SEALED (AES-256-GCM via
  `secrets.seal`), never in plaintext. Aadhaar is never persisted at all.

## RESOLVED 2026-08-19 - the consented-records store

Both of the questions below are answered by one mechanism, and my first analysis of (1) was wrong.

**I claimed local-first clinics could not be a HIP. That was an assumption from a design doc, not from
the code.** Inspecting the implementation showed something more specific: the clinic key is a passphrase
in the device Keychain (`smd_clinic_pw` / `smd_shared_pw`), the server holds no copy, no escrow exists,
and `SMD_getDriveToken` is native-only with `drive.file` scope - so there is no server-side decryption
mechanism at all, rather than an impossibility.

The owner's scenario settled the design: patient treated in Vizag in March presents at KMC Bengaluru in
July; the doctor's phone is off, or he has moved on, or he is mid-clinic. ABDM allows ~20 minutes and a
linked care context can never be withdrawn, so any device-dependent design leaves the patient a context
that never loads - worse than no record, because they get re-tested and delayed.

So **linking a care context is a promise to serve it indefinitely with no human in the loop**, and
`abdm/consented-store.js` is what keeps that promise:
- holds ONLY the records of patients who consented through ABDM, never the clinic database;
- sealed at rest with the Connect master key, blob in R2, index row in D1;
- the object key carries the tenant, the pseudonym and a HASH of the reference - never the reference;
- erased on consent revoke, expiry and ABHA opt-out (`deleteForPatient`), which the state.js sweep
  must call;
- refuses records over 256 KB, because at that size something is embedding a rendering. Store structure
  and narrative and render a PDF on demand - a generated record is 5-20 KB against 100 KB - 2 MB for its
  PDF, and an HIU renders the FHIR itself, so ABDM never needs a PDF from us.

This is not a new security posture: the OPD queue already stores names and mobiles server-side under
`encPHI` with a server-held key, and FollowCare does the same for discharge episodes.

Rejected: escrowing the clinic master key plus server Drive access. It buys the same availability while
letting the server decrypt every patient in every clinic forever, including everyone who never consented,
and the `.smdbak` is one blob so a single-patient request would decrypt the whole clinic into memory.

**Retention:** on the HIP side a record lives as long as its care context is linked - anything shorter
breaks the patient's PHR. The owner's 14-days-then-re-ask rule belongs on the **HIU** side (records we
receive from other hospitals, where ABDM requires deletion on expiry anyway); it is applied there in M3.
