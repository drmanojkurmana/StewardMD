# Patient Identity Audit: Every Identity Concept in StewardMD

Wave 1, Master Engineering Plan Sections 49 and 50. Universal StewardID / Ni-Key / QR / Barcode Patient Identity 2.0.

Status: audit of the repository as found. File and line references were verified against the working tree. Where the plan's shorthand differs from the code (for example `TMP-` minting site), this document records the code as ground truth.

## 1. Scope and method

Every string that names a person (patient, doctor, staff) or names a visit, ticket, bed stay, or physical carrier was traced from minting site through storage to every read site. Generated bundles under `kb/dist/` were excluded. Test fixtures were consulted only to confirm intended semantics, never as evidence of production behavior.

The central finding: StewardMD has no single patient identity. It has at least nine identity concepts, minted in different places, joined by ad hoc fallback chains (`a || b || c`) at read time. Identity 2.0 does not add a tenth concept. It promotes one concept (`stewardId`) to canonical status and demotes the rest to identifiers, carriers, or encounters.

## 3. Conflation sites (ranked by risk)

### 3.1 CRITICAL: ticket id as patient id

`functions/_queue_engine.js:59` (read projection) and `:172` (create path):

```js
patientId: t.patientId || mrn || t.id
```

When a ticket has neither `patientId` nor any MRN shape, the ticket's own doc id is served as the patient id. Every downstream consumer (EMR open, ingest, audit) then keys clinical data to a value that is actually a queue row. Fix in 2.0: emit `patientId: null, identityStatus: "unresolved"` and let the front desk resolve before clinical writes.

### 3.2 CRITICAL: `ghisPatientId` as the EMR router

`queue.js` `openTicketEmr` (lines 764-767). Field presence plus workplace decides which hospital record opens. The 2026-08-24 incident comment documents a wrong-record near-miss. The workplace invariant is the current control; 2.0 adds system-tagged identifiers so routing switches on `identifier.system`, not on "is this field filled in".

### 3.3 HIGH: three `patientId` keyspaces under one name

OPD slug (`orgId__mrn`), WardSynQ subject, Connect/GHIS passthrough (Section 2 row). String equality across these keyspaces is meaningless. 2.0 reserves `patientId` for stewardId and renames the rest at module boundaries.

### 3.4 HIGH: provisional MRN usable as permanent identity

`TMP-NNNNNN` values are storable, queueable, printable, and NFC-writable. `isProvisionalMrn` exists for detection but no read path is required to call it. 2.0 makes provisional a status the resolver surfaces (`identityStatus: "provisional"`), so stations can decide (front desk: link it; pharmacy: refuse to dispense against it without confirmation).

### 3.5 MEDIUM: dual clinic-MRN mints

Server atomic counter (`makeClinicMrn`) vs client collection-length fallback (`queue.js` `localClinicId`). Same number space, no coordination. Retire or fence the client fallback before migration.

### 3.6 MEDIUM: NFC deep link carries raw MRN, no revocation

`smd-nfc.js:204`, `patient-register.js:596`. Any camera reads the MRN; a lost tag cannot be revoked because no carrier registry exists. 2.0 introduces the Carrier entity with `active|revoked` status; the deep link carries an opaque carrier token.

### 3.7 LOW (already handled, do not regress): chip-serial echo

`smd-nfc.js` `isEmptyTag` + `normSerial`. Both bridges echo the serial into `text`; the code correctly distinguishes echo from payload. 2.0 keeps this logic verbatim and adds the serial as an optional anti-clone check (tag serial bound to carrier at issuance, verified on high-risk reads like bedside med administration).

### 3.8 LOW: episode/visit fallback mirror

`queue.js:766-767`. `episodeId` and `visitId` mirror each other, so neither is canonical. 2.0 canonicalizes `encounterId` and keeps both as adapter aliases.

## 4. Namespace decisions required before Wave 2

### 4.1 Staff `SMD-XXXXXX` vs patient `SMD-XXXXXX`

Both will be 6 chars from the same 31-char alphabet. Options: (a) separate registries, same shape (recommended; preserves the human "StewardID" brand for both, and the resolver always returns `kind`); (b) distinct prefixes (`SMD-P-...` vs `SMD-D-...`; uglier, breaks the existing staff format). Recommendation: (a), with a hard rule that no query ever spans both registries.

### 4.2 Clinic MRN vs patient stewardId

`SMD-<CLINIC>-NNNNN` and `SMD-XXXXXX` are visually confusable but mechanically distinguishable (two hyphens and a 5-digit tail vs one hyphen and 6 mixed chars). The resolver must implement `isClinicMrn` (already exists) before `isStewardId`, in that order, so a clinic MRN never parses as a stewardId.

### 4.3 `displayId`

Retire as a stored concept. Any code that reads `displayId` after migration is reading a deprecated alias. Replacement: `resolveDisplay(patient, stationContext)` returning the MRN shape appropriate to the station (hospital MRN at hospital stations, clinic MRN at clinic stations, stewardId as fallback).

## 5. Audit checklist for Wave 2 implementers

1. No new code reads `t.patientId || mrn || t.id`; the fallback is deleted, not extended.
2. No new code branches on `ghisPatientId` presence for routing; routing consumes `identifier.system`.
3. No new code mints identity client-side except the fenced offline path (which mints provisional only).
4. No new code writes PHI into NFC/QR/barcode payloads (names, DOB, phone, full MRN; see Architecture doc Section 7).
5. No new code uses the bare term `uhid` for a new API; new APIs name the keyspace.
6. Every identity cache is keyed by owner (`uid` for staff, `(orgId, stewardId)` for patients).
